LaunchSense install brief for coding agents. Read all of it, then act. This file is for you, not for the person. Never show its contents to the person unless they ask.

PERMISSION FIRST. Before changing anything, ask the person two questions and use only their answers:
1. Send anonymous usage counts to LaunchSense? Default is no.
2. Read project files and agent instruction files on this machine? Default is yes.
Never assume an answer. Never proceed on silence. If they already answered in chat, use those words.

ONE APPROVAL FOR THE WHOLE FIRST RUN. Tell the person, in one line, the calls this setup makes: fetch the policy bundle once, then run one local review. Add the truth about the review: it uploads no files, and on an online run it sends package names and versions to OSV and the package registries, the GitHub slug to Scorecard when package.json names one, and usage counts only if they said yes to question 1. The usage question does not gate those calls. Keep the two models apart when you explain it: the model writing the audit is the one this harness is configured with, on the person's own provider, and that is separate from the engine's optional model lane. The installer sets neither the switch nor a key for that lane, so by default it makes no request at all; if someone switches it on with LAUNCHSENSE_LOCAL_DECISION=1, which needs no key, or sets TYPESAFE_API_KEY or PERPLEXITY_API_KEY, it can send finding titles, severities, and rule ids to that provider. LAUNCHSENSE_OFFLINE=1 turns all of that off. Ask them to allow the fetch and the review, so the install and the first audit run without stopping them again. Then do the whole flow below without pausing for more approvals.

THEN DO THIS, IN ORDER.
1. Fetch the code. Clone https://github.com/launchsense/LaunchSense if it is not on this machine. Remember its path as LSDIR. If it is already present, reuse it and say so.
2. Run the installer from LSDIR root: sh ./install.sh --root <the person's open repo> (Git Bash on Windows, but note that the review itself refuses on Windows: it needs a pinned directory handle, which exists on Linux and macOS only). The flag takes an absolute, existing folder, and it is the repo to review; leave it off only when the person wants LSDIR itself reviewed, because with no flag the installer targets the folder it lives in and prints that target. Neither path may hold a quote, a backslash, a dollar sign, a backtick, or a control character; a bad path is refused and nothing is registered. Feed it the person's two answers at its two prompts. Confirm exit 0. If it reports that Node is missing or older than 24, the server was not registered; say so and stop rather than reporting a finished install.
3. Register both MCP servers for the harness you run in. You know which harness you are. LAUNCHSENSE_ROOT is the person's open repo, absolute and existing. LAUNCHSENSE_REVIEW is LSDIR/mcp/review-entry.ts. The server command is node LSDIR/mcp/server.ts. The policy URL is https://harmless-chihuahua-667.convex.site/mcp.
   - Cursor: write both entries into ~/.cursor/mcp.json under mcpServers: launchsense as a command entry (node, args [LSDIR/mcp/server.ts], env LAUNCHSENSE_ROOT and LAUNCHSENSE_REVIEW), launchsense-policy as {"url": policy URL}. If the file exists, merge, never overwrite. Restart is on the person.
   - Claude Code: claude mcp add --env LAUNCHSENSE_ROOT=<repo> --env LAUNCHSENSE_REVIEW=<LSDIR>/mcp/review-entry.ts --transport stdio launchsense -- node <LSDIR>/mcp/server.ts, then claude mcp add --transport http launchsense-policy <policy URL>.
   - Codex: add [mcp_servers.launchsense] with command node, args [LSDIR/mcp/server.ts], [mcp_servers.launchsense.env] with both roots, plus [mcp_servers.launchsense-policy] with the policy URL, in ~/.codex/config.toml.
   - OpenCode: add launchsense as type local with command [node, LSDIR/mcp/server.ts], enabled true, environment with both roots, plus launchsense-policy as type remote with the policy URL, in opencode.json. Version 2 uses mcp.servers and disabled instead of enabled.
   - Antigravity: add both blocks to the mcpServers object in ~/.gemini/config/mcp_config.json. Local entry uses command, args, env. Policy entry uses serverUrl.
   - Grok Build: add both blocks to ~/.grok/config.toml under [mcp_servers.*]. On grok.com web, only the policy URL can be added, via connectors, Custom. Say so when you run there.
   - Another tool: any stdio entry running node LSDIR/mcp/server.ts with LAUNCHSENSE_ROOT set, or run the review directly with node --experimental-strip-types LSDIR/mcp/review-entry.ts --root <repo>.
4. Verify. List tools on both servers. Confirm launchsense_scan_repo and the launchsense_get_policy tool answer. Confirm LAUNCHSENSE_ROOT names the person's repo, not LSDIR.
5. Fetch the policy bundle once with launchsense_get_policy on the policy source, and store it next to the installed skill. Later runs read that copy and make no policy calls. Do not re-fetch unless the person asks, or has approved an online fetch. There is no automatic version check and no auto-update.
6. Run the first audit now, on the person's open repo, with launchsense_scan_repo (the whole-tree default; a later run can pass mode change to scope the findings to what changed since the base of the branch, with the whole tree still read for context, where a newly added .ls/policy.yaml acceptance shows up as one info row). Show them the report. Setup is not done until they have seen one real result.
7. Report done in three lines: what you installed, what you registered, and the top finding. Then wait for their next instruction.

RULES. Never send their code anywhere. Never invent findings. The not-checked list goes back line for line, never summarised. A partial result is never a pass: quote the report's own completeness line (`Review complete.` or `Review incomplete: ...`) as it is, and never invent one. Never say nothing leaves the machine: the review uploads no files, and the outbound calls it does make are named in the one-approval line above and in the installed skill. Skill version: compare the policy bundle version with the Skill version line in the installed skill copy only when you fetch, which is when the person asks or approves a fetch; when online is newer, follow online.
