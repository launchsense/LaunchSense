# Self-scan log: LaunchSense scanning itself

Public. This is the proof-of-work record: at the end of every build stage we run LaunchSense on this repository, then fix what it finds and record the result. The final entry becomes the published post.

## Why this exists

Three reasons, in order of importance.

1. **It audits us.** Every bug class the product claims to detect, this repo could have. Running it on itself is the cheapest honest test we have.
2. **It finds real defects.** It already found two serious ones in our own code. Both are written up below with what actually happened.
3. **It is the pitch.** A scanner that has scanned itself, published the findings, and fixed them is a stronger claim than any feature list.

## How to read an entry

Each stage records the commit scanned, the raw counts, what we fixed, and what we deliberately did not fix. Counts are never rounded to look better. If a finding is a false positive we say so and why, rather than deleting the line.

## Rules we hold ourselves to

- No cherry picking. Every scan, including the ugly ones, is recorded here.
- Nothing is fixed silently. If a commit fixed a finding, the entry says so.
- A finding we disagree with gets a reason, not a deletion.
- Scans run on the pushed commit, so the SHA in each entry is verifiable by anyone with the repo.
- The report is generated by the product, so the numbers come from the same code path a user hits.

### Stage 7: analyzer integrity fix

Scanned the repository at `1d7d7ba`, the commit that carried those fixes, and again after them.

This scan was the response to an independent verification audit, which found that one of our own recent fixes had introduced a critical defect. Details in `docs/SELF-SCAN-LOG.md` are summarised here:

| Finding | Severity | What we did |
| --- | --- | --- |
| Cached redacted file text fed back into the analyzers | critical | Stopped storing file bodies entirely |
| 2MB byte budget silently unenforced | high | Enforced inside the worker |
| Three modules became order dependent | high | Sorted file list before analysis |
| Two conflicting `hasTests` implementations | high | Extracted one shared module |
| Duplicate dependency detection inverted | medium | Rewrote across manifests |
| `debugger` rule fired on prose | medium | Required a real statement |
| Claim guard could not fail `no issues found` | medium | Tightened the walk-back window |

The most important entry in this log is the first row. We had made file caching store redacted text, to satisfy a privacy claim. That silently removed the exact patterns the secret checks look for, so a **second** scan of the same commit reported fewer secrets than the first. The report looked cleaner than reality, which is the worst direction for a security tool to fail in. Fixed by never storing file bodies at all: only size and content hash are kept.
